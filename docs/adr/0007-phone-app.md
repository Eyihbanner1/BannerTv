# ADR 0007: The phone app

- Status: accepted, first test build for Phase 5 step 3 on the branch `claude/project-thread-woa5lw`
- Date: 31 October 2026

## Context

Phase 5's order is the Android TV app (ADR 0005), the BannerTV account (ADR 0006), then phone apps. On 31 October 2026 Eyitayo asked for the phone app to start alongside the account's LG test round instead of after it, and chose React Native, as the Phase 5 plan said, over showing the LG app's code in a phone-shaped web page.

Four facts shaped the design:

- The Android TV app already runs on phones, but it is the TV's 1920x1080 layout scaled down and held sideways. Eyitayo tried it and found it unpolished. A phone wants its own screens: upright, touch-first, with tabs, sheets and the system's Back.
- Almost everything below the screens (addons, catalogs, the stream finder and its ranking, the playback session, subtitles, Continue Watching, My List, profiles and PINs, Trakt and the account's sync) is plain TypeScript in `packages/core` and `apps/webos/src/data`, `src/player` and `src/i18n`. Writing it again for the phone would make two of everything, and the account only works if both sides store the same things the same way.
- That shared code expects a browser: `localStorage`, `sessionStorage`, IndexedDB, Web Crypto, `window`, `document`, events and a `<video>` element.
- Media3 ExoPlayer plays Matroska, HLS and DASH with the phone's hardware decoders. `expo-video` wraps it on Android (and AVPlayer on iOS).

## Decision

1. **React Native through Expo.** `apps/mobile` is an Expo SDK 58 app (React Native 0.88, React 19, expo-router). The native Android project is generated from `app.config.ts` on every CI run (`expo prebuild`), never kept in the repository. The version is the LG app's, from `appinfo.json`, with the same `versionCode` rule as ADR 0005.
2. **The phone imports the TV's data layer as it is.** Screens import `apps/webos/src` through the `@tv/*` alias and `@bannertv/core` from the workspace. Nothing in `apps/webos/src` changes for the phone. Metro resolves React, React DOM, i18next and react-i18next from `apps/mobile`, so one React runs.
3. **Browser stand-ins, not rewrites.** A Babel plugin (`build/web-globals-plugin.js`) gives the shared files the phone's own `window`, `document`, `localStorage`, `sessionStorage`, `history`, events, `HTMLMediaElement` and `TextDecoder` (`src/runtime/web-globals.ts`). `localStorage` is synchronous SQLite; `sessionStorage`, the address's hash and `window.name` live in memory and survive the app starting itself again, as a page's do across a reload. Metro swaps three modules for phone versions: IndexedDB (`src/shims/idb.ts`, over expo-sqlite), Web Crypto (`src/shims/web-crypto.ts`, over expo-crypto and @noble) and `data/sync-reload` (`src/shims/sync-reload.ts`, which reads the phone's screens instead of the TV's router). Starting the app again, where the TV reloads the page, remounts the screens from a clean store.
4. **The player is the Android TV app's bridge.** `src/player/phone-host.ts` implements ADR 0005's protocol version 1 (`window.BannerAndroid`) over expo-video, and `src/player/video-element.ts` is the `<video>` element the TV's Android engine drives. So the TV's playback session, stream finder and failover, subtitles, Continue Watching and Trakt scrobbling run unchanged. The phone reports itself as `tv: false` with no DTS, TrueHD, Dolby Vision or 4K, and leaves HEVC, AV1 and HDR10 unknown until it reads its decoders. A stream's request headers from its addon (ADR 0005, decision 8) go on every request of that stream through expo-video's `headers` (`src/player/video-source.ts`), with an addon's User-Agent passed as `User-Agent`, the one spelling expo-video reads; values Media3's HTTP client would refuse are dropped, and nothing is kept for the next stream. A subtitle track goes by the title the stream gives it (expo-video's `name`, "Forced", "English SDH"), as the TV app sends Media3's own label, and only then by its language's name (expo-video's `label`, "English"), so a track of forced lines only is known by its title (`isForcedName`, ADR 0003 decision 10; `src/player/tracks.ts`).
5. **Upright, sideways for the film.** The app is portrait. The player turns to landscape while it is open and back after (`src/player/orientation.ts`), hides the system bars, and keeps the screen on while playing. A tap shows or hides the controls, a double tap on either side skips ten seconds, the bar scrubs, and sheets hold audio, subtitles and the stream list. The picture fits whole by default; spreading two fingers on it, or Zoom to fill under More, makes it cover the screen and closing them fits it again (`src/player/picture-fit.ts`). Phones are wider than 16:9, and many film files keep a wide film's black bars inside a 16:9 frame, which fitted whole shows bars on all four sides; filled, those bars are what is cut off. The choice is kept on the phone, not with the profile or the account, since it is about the screen.
6. **Phone screens.** Five tabs (Home, Search, Sports, My List, Settings), with title pages, match pages, catalogs, All streams, the player, Addons, "Who's watching?" and the account pushed over them. Sports follows the TV's rules: the tab shows only while an addon has sports catalogs and never for a kids profile, Home's Live sport row stands in for the sports catalogs, a match asks only the addons that listed it, and a match is never kept for Continue Watching. The player has the TV's Quality menu beside Sources. All streams and the player's Sources have the TV's quick filter as chips over the list (picture size, Cached, addon, audio language and Clear, each shown only while it is on or would change the list; the sizes, addons and languages open a picker with how many streams have each), kept in the same `streamFilter` preference as the TV's. Settings has the TV's Languages and picture as a section of its own (`src/screens/LanguagesSection.tsx`), on the same per-profile preferences. The welcome and the profile picker cover the screens at launch as on the TV. The phone's own strings are added to the TV's English (`src/i18n/phone.ts`), with the lines that speak of a TV or a remote reworded.
7. **The account, Main only.** The phone follows ADR 0006's rules: only Main sees the account; making it, showing the code and deleting it ask for Main's PIN; joining refuses Bring past six profiles. It makes an account with the TV's steps (the setup key when the service needs one, the code to write down, with **Copy the code** beside it, and its last four characters typed back before anything is sent), joins, syncs, shows the code, leaves and deletes, and while the copy Use kept lasts it says what the copy holds and brings it back. Home pulls as it comes into focus (at most once in 30 seconds, counting the account's own pulls) and every 2 minutes while it stays there with the app open, for every profile, so a film paused on the TV shows in Continue watching without pulling to refresh; both grow as the service asks for pulls further apart (`pullMinutes`, ADR 0006 decision 11). On Main, beside that row's heading, it says when the account was last pulled ("Synced 3 min ago"), from the first pull of the launch on, as Settings shows the account's status on Main only. A create left part way offers Show the code and Cancel setting up, as on the TV. The welcome offers Create an account beside Join with a code while the service takes new accounts. Confirmations are the phone's own alerts.
8. **A test package beside the TV app.** The test build is `com.bannertv.app.phonetest`, "BannerTV phone test", so it installs beside the Android TV app's test build on the same phone. It is a release build signed with the Expo template's fixed debug key, so each test APK installs over the last. The store package name and signing are decided with the store listing.
9. **Checked in CI two ways.** The `Phone APK` job first runs the web journeys (`apps/mobile/e2e`): the phone app's web build, held like a phone, against the TV journeys' fake addons, through the welcome, Home, adding an addon, a title, All streams and playing a film, and against their fake account service, making an account and joining it from a second phone. Then it builds the APK (about 20 minutes) and uploads it as `bannertv-phone-apk`: on the combined test build, a run started by hand, the `phone-apk` label, or a `full-ci` pull request whose native side changed (Expo's native fingerprint, see `fingerprint.config.js`, which is also the runtime version of decision 11). A `full-ci` pull request whose native side is unchanged bundles the JavaScript for Android as a check instead. The web build exists for these checks only.
10. **The phone can be the LG's stream helper.** As the Android TV app is (ADR 0005, decision 13). A local Expo module, `modules/stream-helper`, compiles the helper's server and rules from `apps/androidtv/helper-core` as a source folder, so both apps run the same code, and adds the phone's own shell: the foreground service (`specialUse`, as on the TV) with its notification and Stop button, the permissions in its own manifest, and the module `BannerStreamHelper`. `phone-host.ts` puts its `state()` and `command()` on the bridge as `helperState()` and `helper()`, only when the module exists, so the shared `androidHelperState()` reads the same JSON as on the TV. Settings has a Stream helper row in its own section, never for a kids profile and not in the web build, which opens a phone screen (`src/screens/StreamHelperScreen.tsx`, the TV's RunHelper redrawn): a switch, the address and the six-digit code to type on the LG, Forget paired TVs, read again every two seconds while open. From Android 13 the app asks to show notifications before the helper starts. If that is refused the helper still runs, without its notification, and the screen says so.
11. **Signed over-the-air updates from our own Worker.** On 9 November 2026 Eyitayo chose BannerTV's own Cloudflare Worker over Expo's hosted EAS Update, whose code signing needs its $199-a-month plan. The phone takes new JavaScript and images without a new APK through Expo's own client, `expo-updates`, from the `updates` Worker (`https://updates.bannertv.workers.dev/expo/manifest`, with `expo-channel-name: main`). Only an APK of main's own code asks for them, one from a run of CI started by hand on main (`apps/mobile/build/updates.js` reads that from GitHub's `GITHUB_REF`, which every step has): a pull request's or the combined test build's APK runs code main does not have yet, and on main's channel main's next publish would replace it without a word, so those take no updates. The publish workflow signs every update (`rsa-v1_5-sha256`, key id `main`) with the private key that exists only as the `EXPO_UPDATES_PRIVATE_KEY` secret; the Worker serves that signature and never holds the key, and the APK carries the public certificate (`apps/mobile/certs/certificate.pem`) and refuses anything unsigned or signed by another key. An update reaches only APKs with its runtime version, which is the native fingerprint CI already uses (`runtimeVersion: { policy: 'fingerprint' }`). `fingerprint.config.js` now also counts what CI's own checks build an APK for and the fingerprint missed: pnpm's patches, the settings, overrides and patched packages at the top of the lockfile, `pnpm-workspace.yaml`, `.npmrc`, the phone job's machine, Java, prebuild and Gradle command with its `-P` flags and ABI list, and the certificate. Not the version in `appinfo.json`, which goes up for each LG test build and would make every one a phone reinstall. Expo checks at each launch by itself and never holds the launch up for the network; the app checks again whenever it comes back to the front, at most every 15 minutes (`src/runtime/app-updates.ts`). A downloaded update starts when the app starts itself again through `Updates.reloadAsync()` (a join's `reloadAppAsync` runs the same code again), on Home, Settings or the account screen with nothing being typed and "Who's watching?" closed, on screen or off (`src/runtime/safe-restart.ts`). Unlike a join, never from another screen, even off screen: Android counts the app as in the background under a permission prompt or the browser it opened, and the flows that do that wait in the JavaScript for the person to come back (Trakt's sign-in, the stream helper's notifications prompt, an addon's settings page). So never from the player either, even in picture-in-picture. The profile in use stays chosen. Otherwise it starts at the next launch. Settings has a This app section for grown-ups: App version (built in, or the update's short id and when it was published) and Check for updates, which checks, downloads and offers Restart now; Later leaves it until the app is next off screen from one of those screens. None of this runs in the web build or a development build.

## Consequences

- A change to the TV's data layer reaches the phone with no phone work, and a change that breaks the phone shows in the phone's typecheck and journeys.
- The phone carries some TV code it never runs (the remote's focus library comes in through `data/sync-reload`'s original, which Metro replaces, and through type imports). The bundle is about 5.5 MB of Hermes bytecode.
- Code that draws with the remote's focus library cannot be imported. Where a TV screen holds pure helpers (the account's status line and join plan), the phone keeps a copy in `src/data/account-text.ts`, and the stream helper screen's in `src/data/stream-helper-view.ts`. Newer ones go outside the TV's screens instead, so both apps import them: what the copy Use kept holds is worded by `apps/webos/src/data/account-aside.ts`.
- expo-video sends no event when a seek completes, does not say how many channels an audio track has, and the phone has no gzip stream decoder, so gzipped subtitle files from an addon are not shown yet.
- expo-video does not say when the stream marks a subtitle track forced (Media3's `SELECTION_FLAG_FORCED`, which the TV app sends). On the phone a track of forced lines only whose title does not say "Forced" or "Signs & Songs" is taken for a full track, and comes before the addon files, until expo-video gives the flag or a small native change of our own reads it.
- The audio and subtitles panel has the TV sheet's Subtitles, Audio and Timing tabs (`src/player/TracksPanel.tsx`, mounted only while open), its grouping, numbering, notes and row order from the TV's `player/subtitle-versions.ts`: languages with how many versions each has, the open one's versions numbered by source with "Matches your video", "Loading…" or "Couldn't load" before the release name, timing in 0.1 s, 0.5 s and 5 s steps with Reset, and the drift fix. Tapping a language starts its best placed version, the player then choosing the version in it as on the TV (ADR 0003, item 10), and keeps the panel open; picking a version closes it. Subtitles inside the file reach the page as lines (`modules/banner-cues`, below), so Timing moves them too, later but not yet earlier (ADR 0005, decision 6), and their Drift row is hidden, as on the TV.
- The React Compiler is off. The shared hooks read their stores during render, as the TV app (which has no compiler) expects, and the compiler kept their first answers.
- Links from outside the app (`bannertv://`) open Home only (`src/app/+native-intent.ts`), and the account and Addons routes check the profile themselves. Addon install links are the exception: a `stremio://` link and an addon address shared to BannerTV (`modules/banner-share`) are held in memory, never in the route, and open Addons to ask "Add <name>?" once a grown-up profile is in use; a kids profile drops them (`src/nav/addon-links.ts`).
- A local Expo module (`modules/banner-relaunch`) reports a launcher tap on the running app as the bridge's `relaunch`, so a PIN profile or "Ask at launch" asks "Who's watching?" again, as on the Android TV app.
- The stream helper's server lives once, in `apps/androidtv/helper-core`, and its unit tests run in the Android TV job. A change there reaches both APKs, and the phone APK job is what checks it builds on the phone.
- The helper on the phone and the Android TV app's test build on the same phone are separate helpers, each with its own paired TVs. If both are on, the second takes another port, which its address then shows.
- Subtitles follow the profile's subtitle style (size, colour, background and position, chosen on the TV and kept with the profile). `src/player/subtitle-look.ts` scales the TV's sizes and gaps, set for a picture 1080 lines high, to the phone's shorter side, and keeps lines clear of the controls while they show. A second local module (`modules/banner-cues`) listens on the ExoPlayer inside expo-video's `VideoPlayer` and hands over the lines of the subtitle track inside the file as the bridge's `cues` events (ADR 0005, decision 6), so those follow the style and Timing too; picture subtitles (PGS, DVB) are still drawn by Media3. It reaches expo-video's classes through `expoModule.getExpoDependency("expo-video")`, which names expo-video's own project or the prebuilt library autolinking chose for it, and adds Media3 at expo-video's version (1.9.1), which expo-video keeps to itself. Its `Cues.kt` is a copy of the Android TV app's, so both apps hand over the same lines.
- Updates are off until the certificate is committed. Without `certs/certificate.pem`, `app.config.ts` sets `updates.enabled` to false and leaves the signing settings out, so no build can take an unsigned update; the test APKs built so far never take any. Updates start with the first APK of main built after the certificate goes in (Actions, CI, Run workflow, on main), installed over the last as usual.
- Test APKs take no updates. A pull request's APK (the `phone-apk` or `full-ci` label) and the combined test build's keep the JavaScript they were built with, and Settings says the build doesn't take updates. To follow main again after trying one, install an APK of main, which is a full build. Their runtime versions differ from main's too, since the app config the fingerprint hashes differs; CI's comparison of a pull request with its base works both out the same way, so it still sees only native changes.
- What still needs a new APK is whatever changes the fingerprint: a native module added, removed or upgraded (an Expo SDK update included), a config plugin or a native setting in `app.config.ts`, the icons, splash and fonts, the local modules' and the stream helper's Kotlin, pnpm patches and overrides, the phone job's build steps, and a new certificate. Until it is installed, a phone with an older APK simply gets no updates. JavaScript, the TV's shared data layer, strings and images the JavaScript loads arrive over the air.
- If an update crashes before its first screen, expo-updates goes back to the one before it, or to the built-in code. Its own check at launch runs even when an update has broken the app's checks, so a fixed update can always follow, and the Worker can send the phone back to its built-in code.
- expo-updates sends a random id for the install (`EAS-Client-ID`) with each request. The Worker must not log or keep it, as the other Workers keep no request logs.
- Not yet on the phone: Trakt sign-in, editing profiles, Discover, Sports in Search, downloads, casting, picture in picture, tablets and iPhone.
